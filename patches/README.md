# Patches against the vendored framework

Applied in numeric order by `tools/vendor_setup.sh` (`git apply` inside `vendor/yakumo`). `tools/patches.sh check`
applies the series to a clean checkout of the pinned commit and compares it with the vendor tree;
`tools/patches.sh export NNNN-slug` writes a new patch from the vendor tree's uncommitted changes.

| Patch | Kind | Why |
|---|---|---|

Kinds: Layout constant, Bug, Missing feature, Tooling, Speed. Patches that could go upstream are marked in the Why column.
| 0001-embed-nids-verbatim | Bug | `portablekit_add_game` passes `-DINPUT=a.csv|b.csv` to the shell unquoted when a profile ships `config/nids.csv`; the `|` becomes a pipe. Adds `VERBATIM`. Upstream candidate |
| 0002-ring-not-empty-while-aus-pending | Bug | `sceMpegRingbufferAvailableSize` reported the ring empty while the demuxer still held access units (the audio fetch runs ahead and takes the last packs), so a game that ends a movie on an empty ring (Wipeout Pure) dropped its last 16 pictures and never tore the movie down. Reports one packet short of empty while units are queued. Upstream candidate |
| 0003-framebuffer-texture-prefers-exact-target | Bug | `find_framebuffer_texture` picked the most recently drawn target containing a texture's address; Wipeout Pure's bloom blurs 0x04132000, which lies inside the 0x04110000 target, so the blur sampled never-drawn rows (magenta). Prefer a target starting at the address. Upstream candidate |
| 0004-stencil-as-alpha | Missing feature | The GE state ignored the stencil (0x24, 0xDC, 0xDD) and the write masks (0xE8, 0xE9), and every draw stored its fragment alpha, so Wipeout Pure's bloom mask (stencil REPLACE into the 8888 alpha) was full everywhere and the whole race scene bloomed. Parses them into `DrawCall::stencil`, `color_write_mask`, `alpha_write_mask`; the target's alpha is now written only by the stencil zpass op (REPLACE ref, ZERO; KEEP, no stencil test or masked bits leave it), through the fragment shader or, when the colour blend reads source alpha, the alpha blend factors (exact for ZERO, opaque fragments only for REPLACE); whole masked colour channels are not written. Other stencil functions and INCR/DECR/INVERT are logged once. `PURE_NO_STENCIL_ALPHA=1` restores the old path. Upstream candidate |
| 0005-alpha-test-never-always | Bug | The fragment shader read the GE alpha-test function 1 as NEVER and 0 as "no test", but the GE numbers them like the depth test, 0 NEVER and 1 ALWAYS, so every draw that enables the alpha test with ALWAYS was discarded: on Vineta K that is 268 of 871 draws and 87% of the frame (track, barriers, arches, pillars, sky cube). Tests by the GE numbering, pushes ALWAYS for draws without the test and for clears, and compiles the discard out for ALWAYS instead of NEVER. Applies after 0003 (written before 0004 existed). Upstream candidate |
| 0006-shadow-volumes-and-dual-source | Missing feature | Wipeout Pure's ship shadows are depth-fail stencil volumes (zfail INCR/DECR, colour masked) and a full-screen darkening tested GREATER ref 4, which 0004 drew as ALWAYS over the whole opaque world. Each target's depth image gets a stencil aspect (D32_SFLOAT_S8_UINT, else D24_UNORM_S8_UINT), loaded and stored by the render pass; every draw with the stencil on a 5551/4444/8888 target puts its test, ops, reference, compare mask and write mask (~0xE9) in the pipeline key (`stencil`, `stencil_values`; keys file version 3), and a clear of the alpha REPLACEs the stencil with the clear alpha. The stencil is exact and the alpha (what textures, blends, the display and write-back read) is its copy: after a draw the colour path cannot match (`alpha_follows_stencil`), the stencil is copied into the alpha before the next destination-alpha blend and at the end of the pass (`resolve_stencil_alpha`, 9 quads inside the pass from a fixed vertex slot). REPLACE under a colour blend that reads source alpha uses dual-source blending (`kAlphaDual`, SRC1_ALPHA) when the device has `dualSrcBlend`; the other pipelines use a SPIR-V copy with the second output moved off. `PURE_NO_STENCIL_BUFFER=1` (implied by `PURE_NO_STENCIL_ALPHA=1`) and `PURE_NO_DUAL_SOURCE=1` turn the parts off; `PURE_TRACE_STENCIL_COPY=1` logs each copy. Upstream candidate |
| 0007-free-target-descriptors-before-pool | Bug | `VulkanRenderer::shutdown()` destroyed `descriptor_pool` and only then the render targets, whose `destroy_target` frees each target's two copy descriptor sets (made when the game samples a framebuffer, as Wipeout Pure's bloom does) back to that pool. Under MoltenVK the pool and its sets are heap objects, so `vkFreeDescriptorSets` wrote into freed memory: the "Heap corruption detected, free list is damaged ... Incorrect guard value" abort (or a hang while the crash report was written) after a race's frame exit (task 015). Destroys the targets, the held picture and the interpolation targets before the pool. Upstream candidate |
| 0008-depth-write-back-at-signal | Missing feature | The renderer kept depth in per-target Vulkan images and never stored it in guest VRAM, so Wipeout Pure's lens flare, whose GE SIGNAL 0x0200 handler reads a 4x4 block of the depth buffer around the sun with the CPU (through the 0x04600000 mirror), always read zeros (open sky) and was never occluded. Before a SIGNAL interrupt with a signal function is queued, `write_back_depth` copies the depth aspect of the GE's current colour target into a mapped buffer, runs the frame recorded so far and waits (as `read_back_framebuffer` does), and stores z = depth x 65535 as 16-bit pixels in rows of the depth stride at the depth address (480x272; screen-wide buffers, stride 480 or more, only). Depth images get TRANSFER_SRC usage. About 1 ms a race frame on the M4 Pro, 0.9 of it the GPU wait. `PURE_NO_DEPTH_READBACK=1` turns it off; `PURE_TRACE_DEPTH_READBACK=1` logs each write-back. Upstream candidate (a per-game switch in `GameProfile` would keep the wait off games that never read depth) |
| 0009-ge-backend-seam | Missing feature | The GE backend seam of D-003 (docs/ge-backend.md): `gpu::GeBackend` (`host/gpu/ge_backend.hpp`) with a registry (`register_backend`, `make_backend`, `BackendRegistration`) and `<prefix>_GE_BACKEND` (vulkan when unset). The HLE (`hle_media.cpp`) hands draws, block transfers, read-backs, the frame and depth write-backs, CPU pictures, captures and the draw/frame counters to the backend, and keeps the window shell (`VulkanRenderer`: window, pad, input script, interface, present, pacing) for the rest. `vulkan` forwards each call to the renderer method that did the work before (`vulkan_ge_backend.cpp`, no change in output; the renderer gains `display_image()`, which names the target `present()` shows). `null` draws nothing, presents black and counts draws, and needs no window: with `<prefix>_NO_RENDER` set it is the only backend that runs, without a window or GPU. `record` wraps another backend (`<prefix>_GE_RECORD_INNER`) and writes frames `<prefix>_GE_RECORD_AT` to `+<prefix>_GE_RECORD_FRAMES-1` to `<prefix>_GE_RECORD`: every call with the guest memory it read and each frame's presented image (`ge_record_format.hpp`, read by `tools/gerec/gerec_dump.py`). Adds the four sources to `cmake/PortableKit.cmake`. Upstream candidate |
| 0010-shell-seam | Missing feature | The shell seam of D-007 (docs/ge-backend.md section 8): `host::Shell` (`host/shell/shell.hpp`: lifecycle, events and input, presenting, interface) with a registry (`register_shell`, `make_shell`, `ShellRegistration`) and `<prefix>_SHELL` (vulkan when unset; `<prefix>_NO_RENDER` means headless). The HLE (`hle_media.cpp`) owns a shell and a GE backend and talks to nothing else: `ensure_shell_and_backend()` makes the shell, then the backend (the Vulkan backend only in the Vulkan shell), `present_frame` shows the backend's image through `Shell::present`, and sceCtrl samples the shell's pad. `vulkan` (`vulkan_shell.cpp`) owns the `VulkanRenderer` and forwards each call to it unchanged (a Cpu image from another backend is uploaded into the display target first); `active_renderer()` gives the renderer only under it, for what needs Vulkan itself. `headless` (`headless_shell.cpp`, no SDL or GPU) reads the input script and the live file at pad level, one script frame per flip: `pad` and `axis` set the pad as the SDL shells map their gamepad, `shot` writes the GE backend's `capture_frame`, `quit` ends the run, key/mouse/text steps are reported once. Shared pieces moved out of the renderer and the interface: the SDL pad sampler (`sdl_pad.cpp`, the renderer's `Impl` derives from it), the gamepad-to-PSP mapping with SDL's button and axis names (`gamepad.cpp`), the input script's grammar (`script_steps.cpp`). The interface layer attaches to a `Shell` with a window (`Layer::attach(host::Shell &)`); the menu's resolution, texture filter and texture pack rows use the Vulkan renderer through `active_renderer()`. Adds the six sources to `cmake/PortableKit.cmake`. No change in what the Vulkan path shows (the frame regression captures are pixel-identical). Upstream candidate |
| 0011-host-wait-real-time | Behaviour (headless pace) | `Kernel::advance_clock` slept up to 1 ms of real time per clock step while any thread was in a `WaitType::Host` wait, so a network wait would see real time pass; `user_main`'s `sceKernelWaitThreadEnd` is such a wait for the whole run, which held every unpaced (headless) run to about 19 frames a second. `wait_host` takes `real_time` (only the adhoc network waits pass it) and the sleep applies to those alone; `Kernel::set_paced(bool)` lets the HLE pace the clock by the shell (a shell with a window is paced, the headless one is not), with `<prefix>_NO_RENDER` deciding until the shell exists. Headless frontend route: 2200 frames in 1.1 s instead of 115 s, same draws, same events. Windowed runs unchanged. Upstream candidate |
| 0012-ui-platform-init-in-shell | Missing feature | `Layer::attach` started ImGui's SDL3 platform backend with `ImGui_ImplSDL3_InitForVulkan` for every shell, which is wrong for a shell that draws with another API (the Metal shell, task 027, needs `ImGui_ImplSDL3_InitForMetal`). The platform init moves into `Shell::initialize_ui`: the Vulkan shell calls `ImGui_ImplSDL3_InitForVulkan` for its renderer's window before the renderer's ImGui Vulkan backend (and shuts both down, or leaves neither running on failure), and `Layer::attach` loads the fonts, calls only `shell.initialize_ui`, then sets the gamepad mode. Nothing else in `ui/` changes; the Vulkan path is unchanged (frame regression 5/5 with the same fractions). Upstream candidate |
| 0013-texture-mapping-modes | Missing feature | The GE state ignored TEXMAPMODE (0xC0: the map mode in bits 0..1, the texture matrix's source TEXPROJMAP in bits 8..9) and TEXSHADELS (0xC1: the two lights of an environment map in bits 0..1 and 8..9), so no backend could draw Wipeout Pure's environment-mapped draws (the ships' hulls and canopies, glass and shiny roofs: 46 to 125 draws a race frame) or its texture-matrix draws (40 on Vineta K) other than with their UVs. Parses both into `DrawCall::texture_map` (`TextureMapState`: `map_mode`, `proj_source`, `shade_light_u`, `shade_light_v`), so they leave the ignored-command list. The record format (`ge_record_format.hpp`) writes the four as u32 at the end of a Draw, and the reader takes a Draw that ends before them (every recording made before) as map mode 0, so old recordings replay as they did; `kVersion` stays 1. The Vulkan renderer is unchanged: it still draws every draw with its UVs (a comment says so). Upstream candidate |
| 0014-texture-mip-levels | Missing feature | The GE state ignored a texture's mip levels: TEXADDR1 to 7 (0xA1 to 0xA7), TEXBUFWIDTH1 to 7 (0xA9 to 0xAF), TEXSIZE1 to 7 (0xB9 to 0xBF), the level count in TEXMODE (0xC2 bits 16..18), TEXLEVEL (0xC8: the level mode in bits 0..1, a signed bias in 1/16 levels in bits 16..23) and TEXLODSLOPE (0xD0), so no backend could sample the smaller levels Wipeout Pure gives 70 to 87% of its textured race draws, and distant textures shimmered. `TextureState` carries them (`level_count`, `levels[7]` of `TextureLevel`: address, buffer width, width, height; `level_mode`, `level_bias`, `lod_slope`), so 23 commands leave the ignored-command list. The record format writes them at the end of a Draw (`Writer::put_levels`, `kLevelBytes`), and the reader takes a Draw that ends before them (every recording made before) as one level; `kVersion` stays 1. The Vulkan renderer is unchanged: it samples level 0 (a comment says so). `record_backend.cpp` still records level 0's texels alone (see docs/metal-backend.md, "Mipmaps"). Upstream candidate |
| 0015-savedata-list | Missing feature | `hle_savedata.cpp` answered LISTSAVE with the first listed name and LISTLOAD with the first save that exists, so Wipeout Pure's second profile overwrote its first and LOAD offered no choice (fidelity difference 4, task 039). A list request (LISTLOAD, LISTSAVE, LISTDELETE, and mode 7 without a save name, which Wipeout Pure's PROFILE > DELETE sends and a PSP answers with a list of the game's saves) now takes, in order: the input script's new `save ANSWER` step (a save name, a 0-based position, `newest`, `free` or `cancel`; queued by both script readers in `shell/script_steps.cpp`, so headless runs answer it too); the save list (`ui/save_list.cpp`, new; hooked into `draw_over_game` and kept from the menu like the on-screen keyboard), when there is a choice and an interface: drawn over the running game in the PSP dialog's layout (banner, a column of `ICON0.PNG` icons with the game's newData icon for free slots, stb_image into ImGui user textures, the save's title, date, time, size and detail, NEW DATA), the request staying VISIBLE while the game polls, with the PSP's overwrite and delete questions (No first), "Save completed." and the result written when it closes (cancel: 1); Enter and Back follow the request's buttonSwap through the pad mapping; otherwise the newest save to load, the first free slot to save to, only the named save to delete, and a cancel rather than writing over or deleting anything. A list request while another's list is open closes it as cancelled. Adds `host/ui/save_list.cpp` to `cmake/PortableKit.cmake`. Upstream candidate |
| 0017-colour-test-dither-clip | Missing feature | The GE state ignored the colour test (COLORTESTENABLE 0x27; COLORTEST 0xD8: the function in bits 0..1, 0 NEVER, 1 ALWAYS, 2 EQUAL, 3 NOTEQUAL; COLORREF 0xD9 and COLORTESTMASK 0xDA, 0x00BBGGRR), dithering (DITHERENABLE 0x20 and the matrix DITH0 to DITH3, 0xE2 to 0xE5: DITHn is the row for y & 3 == n, four signed 4-bit offsets, column x & 3 at bits 4 x (x & 3)) and CLIPENABLE (0x1C), so no backend could drop the pure black pixels Wipeout Pure's glow sprites and billboard content test away (3 to 14 draws a race frame, fidelity difference 10), dither its 565 billboard target (difference 11) or clamp depth as the GE does with CLIPENABLE on (every 3D draw). Parses them into `DrawCall::color_test` (`ColorTestState`), `dither` (`DitherState`, with `offset(x, y)`) and `clip_enabled`, so 10 commands leave the ignored-command list (30 distinct remain, from 40). The record format writes them at the end of a Draw (`kPixelBytes`), and the reader takes a Draw that ends before them as no colour test, no dithering and CLIPENABLE off; `kVersion` stays 1. `RecordBackend::submit` now also records the texels of every mip level a draw samples (levels 1 to `level_count` - 1 when the minification filter's bit 2 is on), so a recording made since patch 0014 replays mipmapped draws from their own texels instead of zeroed memory. The Vulkan renderer is unchanged: it draws none of the three (a comment says so). Upstream candidate |
| 0018-sas-reverb | Missing feature | The software SAS accepted `__sceSasRevType`, `__sceSasRevParam`, `__sceSasRevEVOL` and `__sceSasRevVON` and dropped them, and `__sceSasSetVolume`'s effect sends (its fifth and sixth arguments) with them, so a game's reverb never sounded: Wipeout Pure asks for HALL from the race load on, and its effects stopped dead at a pause where PPSSPP's ring on for half a second (fidelity difference 12, task 043). `SasCore` gains a reverb unit, `SasReverb`: the PlayStation SPU's reverberator from its public documentation (psx-spx, "SPU Reverb Formula" and "SPU Reverb Examples": the same-side and different-side reflections, four combs, two all-pass filters in a ring of 16-bit samples, every intermediate saturated), the nine presets by `__sceSasRevType` (1 ROOM to 9 PIPE; anything else OFF, a new type starting from a silent ring), RevParam's delay and feedback shaping ECHO and DELAY (inferred from those two tables, which differ only there), the voices' effect sends summed as the dry mix is, the unit's output added at the wet volumes when the wet switch is on and the dry mix kept or dropped by the dry one. Two departures from the SPU, both measured against PPSSPP's output of the game: the formula steps once a sample at the SAS's 44100 Hz, not at 22050 Hz between the SPU's resampling filters (at 22050 Hz the tail lasts three times as long), and the sends enter at half their volume (the wet level is half the unity reading's at every 100 ms step of a decay). Type 0, the wet switch off, or `<prefix>_NO_REVERB=1` leaves the output exactly as before; `<prefix>_SAS_REVERB_SPU_RATE=1` runs the SPU's rate and filters. About 4 us of host time a 256-frame grain (5.8 ms) on the M4 Pro; `<prefix>_TRACE_AUDIO`'s per-second line adds `reverb=TYPE reverb_us=N`, and `<prefix>_TRACE_SAS` prints each change of a voice's sends and of the four reverb calls. Upstream candidate |
| 0019-savedata-no-key-mode | Missing feature | `hle_savedata.cpp` wrote a save plain whenever the request carried no game key, but a PSP (and PPSSPP) writes such a save in the save-data utility's no-key mode, mode 1: Wipeout Pure's 0x5DC-byte block (the firmware 1.x layout, no key field) got a plain `PROFILE.BIN` that no PSP would load, and PSP and PPSSPP saves, which are mode 1, met a hash check that refused them (fidelity difference 5, task 045). A request without a key (the short block, or a zero key) now sets `SaveFiles::no_key_mode` when the console's keys are available (`savedata_keys_available()`), and `write_save` then enciphers the data file in mode 1 with the console's keys alone, stores it at the data's own length plus the 16-byte header (41586 bytes for the 41570 of a profile, as PPSSPP's), lists its hash in `SAVEDATA_FILE_LIST` and signs `SAVEDATA_PARAMS` (flag 0x01, the mode-1 hash of PARAM.SFO; `write_flags()` says which). `data_file_hash` hashes a file whose length is not a multiple of 16 as if padded with zeros, which is what the PSP's hash covers (the framework only ever wrote padded files, so its own saves hash as before; PPSSPP's 41586-byte file failed without it). `load_save` checks PARAM.SFO's own hashes before the data file's for every encrypted save, as the import check does, and reports the flag and whether the file's listed hash was checked; `do_load` logs `PROFILE.BIN: mode 1 (no game key), PARAM.SFO's hash verified, the file's hash in SAVEDATA_FILE_LIST verified, decrypted` on a line of its own and a failed hash as `broken save in ...` with result 0x80110306, and `do_save` logs the mode-1 write likewise (the `saved`/`loaded` lines keep their form). A plain save (flag 0, every save the port wrote before) still loads as it is; without the keys the behaviour is the old one. No key material: every key comes from `crypto_keys()` by slot. Upstream candidate |
| 0020-vfpu-dot-rounding | Fidelity (D-013) | The framework computed every VFPU dot product as one C++ expression (`vdot`, `vhdp`, the dot lanes of `vcrsp` and `vqmul` in `allegrex_context.hpp`; the rows of `vtfm` and the elements of `vmmul` as loops the codegen emits inline), which clang contracts into fused multiply-adds, so the port rounded differently from the PSP and from PPSSPP (task 047: 20 percent of one site's `vdot.t` results off by 1 ulp, and the AI's race parting from PPSSPP's over seconds). `AllegrexContext::vfpu_dot` now rounds as a real PSP does (pspautotests' rule: exact products with a raw exponent sum, zeros and subnormals skipped, aligned to the largest exponent with two extra bits, truncated toward zero, summed exactly, cut to 24 bits toward zero, flushed below the smallest normal; infinities and NaNs on the unfused IEEE path), the `_ct` and runtime `vdot`, `vhdp`, `vcrsp` and `vqmul` use it, `codegen_main.cpp`'s Vtfm and Vmmul emitters call it instead of their loops, and the generated units are compiled with `-ffp-contract=off` so every translated instruction rounds on its own. `vfpu_dot_mode()` 1 (test only: our profile sets it under `PURE_TEST_RACE_CLOCK` or `PURE_VFPU_DOT=ppsspp`) gives PPSSPP's JIT rounding instead (a fused chain in lane order for vectors, unfused from +0 for matrix elements) for the scorecard's comparisons. Upstream candidate (the rule; the mode is ours) |
